# pi-rtk-surveyor review (2026-10-03)

Reviewed at commit 4ea4af0 (last commit 2025-07-18). Untracked notes, not part of the repo.

## Recommendation first: the dev loop

Use **USB gadget mode on the Zero 2 W's OTG port** as the primary link from MS-R1 #1,
one cable per Pi, with a **composite gadget (`g_cdc`: CDC-ECM network + CDC-ACM serial)**.
That one cable gives power, a wired SSH/rsync link that does not depend on Wi-Fi, and a
login console (`serial-getty@ttyGS0`) that keeps working when networking is broken.
Wi-Fi SSH is the second path, for untethered and field tests. A GPIO USB-UART cable is only
for pre-kernel boot problems, and only with the GNSS HAT unstacked (see the UART
conflict below).

Why not the GPIO UART console: the Zero 2 W (RP3A0/BCM2837) has exactly one usable UART on
the header (GPIO14/15). The LC29H HAT needs it, and needs it to be the PL011
(`dtoverlay=disable-bt`), not the mini UART, for reliable 115200 with RTCM in both
directions. So `console=serial0` has to come off `cmdline.txt`, and the header console is gone
on a stacked unit. There is no UART2-5 on this SoC (that is BCM2711 and later).

Why not Wi-Fi only: 2.4 GHz only, chip antenna, power-save on by default (SSH stalls,
dropped rsyncs), and the AP may isolate clients. It still has to work for the field, so
configure it, just don't make the inner loop depend on it.

## What the repo is

DIY RTK surveying: two Pi Zero 2 W units, one base and one rover, each with a Waveshare
LC29H GNSS RTK HAT and a Waveshare 1.3" OLED HAT. Pick BASE or ROVER from an OLED menu at
boot, the base sends RTCM3 to the rover over a Wi-Fi hotspot, and the rover logs points to
CSV for CAD.

- Stack: Python 3, venv, luma.oled (SH1106 over SPI0), RPi.GPIO/gpiozero/lgpio (all three),
  pyserial and pynmea2, Flask with Flask-SocketIO dashboard, a systemd unit and a `setup.sh` that
  runs `apt upgrade`, makes the venv and enables the service.
- Size: 42 commits over 10 days (2025-07-08 to 07-18). About 5k lines in 30 real files,
  plus **29 zero-byte placeholder files** (config, logging, nmea_parser, screens, utils,
  battery, gps_monitor, base and rover status). No tests, and `tests/` and `scripts/` from
  the README don't exist.
- Hardware it assumes (from code and docs):
  - **GNSS**: Quectel LC29H on the Waveshare LC29H(XX) GPS/RTK HAT, UART at
    `/dev/ttyAMA0`, NMEA only.
  - **Display**: Waveshare 1.3" OLED HAT, SH1106 128x64, SPI0 (CE0 GPIO8, MOSI 10,
    SCLK 11, DC GPIO24, RST GPIO25), mounted rotated 180 degrees. Keys KEY1/2/3 on GPIO
    21/20/16, joystick up/down/left/right/press on 6/19/5/26/13.
  - **Power**: a USB power bank. Battery monitoring is a placeholder.
- Deployment: `git clone` on the Pi, then `setup.sh`, then a systemd service running
  `venv/bin/python src/main.py`. Development was done directly on the Pi.

## State: what works and what doesn't

Only the OLED splash and menu, buttons (polled), and a system-info screen were plausibly
working. The core of the project was never built:

- **No RTCM and no NTRIP code anywhere.** The base never configures the LC29H as a base,
  never reads RTCM, and never serves it. The rover never receives corrections. "Wi-Fi
  hotspot" is `self.wifi_hotspot_running = True  # TODO`. Rover "Connected to base" is a
  placeholder. Point logging is a `TODO: Save to CSV`.
- GNSS serial defaults to **38400 baud**. The LC29H ships at 115200, so `connect()` probes
  `ttyAMA0`, `ttyS0`, `ttyUSB0` and `ttyACM0`, sees no `$` within 2 s, and fails.
- Accuracy is never parsed (no GST/PQTM accuracy sentences), so `accuracy_horizontal`
  stays at 99.9 forever.
- `get_position()` returns the shared mutable object, so the lock does nothing.
- `gpio_manager.py` mixes **physical pin numbers** (`RESERVED_PINS`: 8 = "UART0_TXD",
  19/21/23/24/26 = SPI) with **BCM numbers** (OLED and button maps) in one table. BCM8,
  19, 21, 24 and 26 collide with "reserved" physical numbers.
- The README lists "battery monitoring", "systemd" and "multiple display modes" as done;
  battery is `psutil.sensors_battery()`, which is always None on a Pi. A `simulate` mode
  imports a nonexistent `tests.mock_gps`, which contradicts the README's no-simulation rule.
- The web UI loads socket.io from `cdn.socket.io`. That fails in the field on the base's
  own hotspot (no internet).
- `requirements.txt` pins `python-wifi` (a Python 2 era package), pulls numpy for an
  OLED, and pip-builds pillow/numpy on a Zero 2 W (slow, 512 MB RAM).
- The systemd unit uses deprecated `MemoryLimit=` and puts the venv in the home dir with
  `ProtectHome=false`.

**Verdict: the owner is right, rewrite from scratch.** About 80% is scaffolding around a
GNSS and corrections core that doesn't exist. Keep these:

- the pin map (BCM numbers above)
- the SH1106 rotate=2 finding
- the UX flow in `docs/workflow.md`
- the CSV point schema in `docs/thoughts.md`

## Hardware notes for two units

- **Check the LC29H variant on each HAT.** Waveshare sells the LC29H(DA) (RTK rover,
  takes RTCM3 in) and the LC29H(BS) (base, outputs RTCM3 MSM, survey-in or fixed
  position via `$PQTMCFGSVIN`). The base must be a BS. A DA cannot be a base. Query with
  `$PQTMVERNO*58` at 115200. If both are DA, the base role becomes "use a public
  caster": RTK2go, state CORS/RTN, or Onocoy. Then one unit could be the rover and the
  other a spare.
- **UART**: GPIO14/15. Use `enable_uart=1` and `dtoverlay=disable-bt` (puts PL011
  `ttyAMA0` on the header; use `/dev/serial0`), and remove `console=serial0,115200` from
  `cmdline.txt` (`raspi-config nonint do_serial_cons 1` / `do_serial_hw 0`).
- **Pins between the HATs**: the OLED HAT uses SPI0, 24, 25, 21, 20, 16, 6, 19, 5, 26
  and 13. The LC29H HAT uses 14/15 plus possibly PPS/RESET/WAKEUP lines, depending on the
  revision. Check the Waveshare schematic for PPS and reset GPIOs before assigning
  anything else. If the HAT revision has an onboard USB-UART port with a UART-routing
  switch, that port can serve as a console/GNSS-config path on the bench.
- Bench: the GNSS needs sky. Run a long antenna coax to a window or the roof. RTK fix
  indoors won't happen.

## What a rewrite should look like

- **Language**: Zig (already on #1). One static `aarch64-linux-musl` binary, no runtime,
  no pip on the Pi, a sub-second start. Everything needed is plain Linux uAPI:
  - termios for the UART
  - `spidev` ioctl for the SH1106 (about 100 lines; page addressing, 2-column offset)
  - GPIO char-dev v2 line events for the buttons (no RPi.GPIO)
  - std.net for NTRIP
  - an embedded 6x8 bitmap font

  If library leverage matters more than toolchain consistency, Go
  (`go.bug.st/serial`, periph.io) is the pragmatic alternative. Avoid Python on the
  Zero 2 W for the daemon.
- **OS**: Raspberry Pi OS Lite **64-bit**, so #1 builds for the same arch and ABI. musl
  static avoids glibc-version coupling between #1's Debian and Pi OS.
- **Process layout**: one daemon, `rtkd`, with the role fixed per unit in config. The
  boot menu is only an override. Threads or one poll loop:
  1. **gnss**: owns `/dev/serial0` and demuxes the byte stream into NMEA lines (`$...\r\n`)
     and RTCM3 frames (0xD3, 10-bit length, CRC24Q checked). Writes config commands.
  2. **corrections**: the base runs a minimal **NTRIP caster** on :2101 (one mountpoint,
     sends the RTCM frames as they arrive; optional NTRIP-server push to RTK2go). The rover
     runs an **NTRIP client** (to the base, or to any public caster), writes RTCM to the
     UART, and sends GGA upstream every 10 s for VRS casters. Plain NTRIP means RTKLIB
     `str2str`, SW Maps or Lefebure can stand in for either side while testing.
  3. **ui**: SH1106 at 2-5 Hz (fix type, sats, age of corrections, hAcc/vAcc, battery,
     point count) and button events.
  4. **log**: survey points to CSV and GeoJSON (fsync each point). Raw GNSS stream to a
     rotating file (for post-processing in RTKLIB if RTK fails in the field). Operational
     logs to stdout, which goes to the journal.
  5. Optional: tiny HTTP status and download page with all assets embedded.
- **Link**: both units join one Wi-Fi network (a phone hotspot or a travel router at the
  base). That beats a Zero 2 W soft-AP on range and stability. Keep the
  rover-to-caster address in config.
- **Config**: `/etc/rtk/rtk.conf` (INI/ZON). Fields: role, uart, baud, caster
  host/port/mount/user/pass, base mode (`survey_in secs,acc_m` | `fixed lat,lon,h`),
  log dir. Validate at start and show errors on the OLED.
- **systemd**: `rtkd.service`, `Type=simple`, `Restart=always`, `User=rtk` with
  `SupplementaryGroups=dialout spi gpio`, `StateDirectory=rtk`, `ProtectSystem=strict`.
  Optional overlayfs root (`raspi-config nonint do_overlayfs 0`) for power-pull
  safety in the field, with data on a separate rw partition.

## Concrete dev loop (MS-R1 #1 to two Zero 2 Ws)

### Provision the SD cards headless (once per card; needs the owner's sudo for `dd`)

```sh
# scripts/provision-sd.sh <dev> <hostname> <usb-subnet-octet>   e.g. /dev/sdX rtk-base 11
xzcat 2025-*-raspios-*-arm64-lite.img.xz | sudo dd of=$DEV bs=4M conv=fsync status=progress
sudo mount ${DEV}1 /mnt/boot
# config.txt
printf '\n[all]\nenable_uart=1\ndtoverlay=disable-bt\ndtoverlay=dwc2,dr_mode=peripheral\ndtparam=spi=on\n' | sudo tee -a /mnt/boot/config.txt
# cmdline.txt: drop serial console, load the composite gadget
sudo sed -i 's/console=serial0,115200 //; s/rootwait/rootwait modules-load=dwc2,g_cdc/' /mnt/boot/cmdline.txt
# Fixed gadget MACs so #1's NetworkManager profile binds to the right Pi
#   -> cloud-init write_files: /etc/modprobe.d/g_cdc.conf =
#      "options g_cdc host_addr=02:52:54:4b:00:$OCT dev_addr=02:52:54:4b:01:$OCT"
sudo cp user-data network-config meta-data /mnt/boot/   # cloud-init (Trixie images); Bookworm images: use Imager's customisation instead
```

`user-data` (cloud-init) does the following:

- sets the hostname
- creates user `rtk` with #1's `~/.ssh/id_ed25519.pub`, password login off
- writes `/etc/modprobe.d/g_cdc.conf`
- writes NM keyfile `/etc/NetworkManager/system-connections/usb0.nmconnection`
  (`ipv4.method=manual`, `address1=10.55.$OCT.2/24`, `ipv6.method=link-local`, mode 0600)
- writes the office Wi-Fi keyfile with `wifi.powersave=2`
- `runcmd`: `systemctl enable serial-getty@ttyGS0`,
  `raspi-config nonint do_serial_cons 1`

Raspberry Pi Imager's GUI (hostname, user and key, Wi-Fi, SSH) is an acceptable
fallback for the basics. The config.txt and cmdline.txt edits are still needed.

### Host side on #1 (once, owner with sudo or a polkit-allowed nmcli)

```sh
nmcli con add type ethernet con-name rtk-base ifname '*' 802-3-ethernet.mac-address 02:52:54:4b:00:11 \
      ipv4.method manual ipv4.addresses 10.55.11.1/24 ipv6.method link-local
nmcli con add type ethernet con-name rtk-rover ifname '*' 802-3-ethernet.mac-address 02:52:54:4b:00:12 \
      ipv4.method manual ipv4.addresses 10.55.12.1/24 ipv6.method link-local
# ~/.ssh/config: Host rtk-base -> 10.55.11.2, Host rtk-rover -> 10.55.12.2, User rtk
# Wi-Fi fallback: Host rtk-base-wifi -> rtk-base.local (needs avahi on #1; not installed today)
```

Console when the network is broken: `picocom -b 115200 /dev/ttyACM<n>` (the ACM half of
the gadget; the udev `by-id` path is stable). It is not `/dev/ttyUSB0`, which stays with
MS-R1 #2's capture.

### Inner loop scripts (in the new repo)

```sh
# scripts/deploy.sh <host>
zig build -Dtarget=aarch64-linux-musl -Doptimize=ReleaseSafe
rsync -az zig-out/bin/rtkd $1:/tmp/rtkd.new
ssh $1 'sudo install -m755 /tmp/rtkd.new /usr/local/bin/rtkd && sudo systemctl restart rtkd'
ssh $1 'journalctl -u rtkd -f -o short-monotonic'          # scripts/logs.sh <host>

# scripts/run.sh <host> [args]  -- foreground run for debugging (service stopped)
ssh -t $1 'sudo systemctl stop rtkd; /tmp/rtkd.new --config /etc/rtk/rtk.conf --verbose'

# scripts/gnss-tap.sh <host>  -- raw receiver bytes without the daemon
ssh $1 'sudo systemctl stop rtkd; stty -F /dev/serial0 115200 raw; cat /dev/serial0' | tee gnss-$(date +%s).log
```

Bench RTK with both Pis cabled to #1: the base serves NTRIP on 10.55.11.2:2101. Have the
rover reach it through #1 (`net.ipv4.ip_forward=1` plus a route on each Pi). Or run the
caster relay on #1 (`str2str -in ntrip://10.55.11.2:2101/BASE -out ntripc://:2101/BASE`)
and point the rover at 10.55.12.1. The field config only swaps the caster address to the
Wi-Fi one.

Power: the OTG port backfeeds 5 V, so a Pi with both HATs (roughly 300-500 mA) runs off a
#1 USB port. Use a USB 3 port or a powered hub, because the active antenna adds load.
